## Agents

- Spec: `packages/spec/src/agent.ts` (`agentSchema`, colour is an index into `--dash-series-N`, reach in `access.ts`'s own words). Permission: `agents.manage` (owner, admin).
- Server: `apps/server/src/agents/` (`AgentStore`, `AgentService` — one place for the routes and the chat to share), `routes/agents.ts`, chat actions in `chat/agent-actions.ts`. Table `dash_agents` in `platform/db.ts`.
- Web: `#/agent/<section>[/<id>]` in `apps/web/src/route.ts`; `agent/AgentShell.tsx` picks the section; the shared `AgentChip` is in `packages/components/src/ui/`.
- Replies: `role`, `instructions`, `personality` sit on `BASE_RESPONSE_PROMPT` via `composeResponsePrompt` (`packages/spec/src/agent-prompt.ts`). **Only for an agent replying to a person**; workflow steps never use it. Generate is `POST /api/agents/assist` (`agents/assist.ts`, model task `agent`).
- Knowledge: per agent (`knowledge.notes`, `knowledge.context` rules: plain-words trigger + endpoints to read) and shared (`/api/agent-knowledge`, table `dash_agent_shared`). An agent rule may only read connections its reach reads; a shared rule is checked per agent when it fires.
- Tools: `tools[]`, each `auto | approve | deny` with a deny reply. A record tool that acts needs `reachCovers` its permission (`AgentService.toolProblems`). `run_workflow` names a workflow whose trigger is `agent` (`AgentService.workflowProblems`), and `POST /api/agents/:id/tools/:toolId/use` uses it the way a conversation will. A `highlight` tool (title in `label`, `description`) is not a reply tool: every message received is checked against all active highlights (`agents/highlights.ts`, `checkHighlights`) and a match goes to a `HighlightNotifier`; Comms wires both.
- Anything later steps label with an owner should store `{ kind: "agent" | "member"; id }`, not a bare agent id. Approval vs automatic belongs to the workflow action, not the agent.

## Workflows

- Spec: `packages/spec/src/actions.ts` is the action catalog (`ACTION_BASES`, `ACTION_VARIANTS` with fields, outcomes, outputs, body kind, `leavesDash`, `reversible`, `modelTask`; helpers `actionVariant`, `outcomesFor`, `missingFields`, `fieldProblems`). `packages/spec/src/workflow.ts` is the workflow (`trigger`, `nodes`, `edges` `{from, outcome, to}` with `from: "trigger"` for the start, `limits`, `trial`, `triggerLimits`, `guardrails`), the case (`workflowCaseSchema`: data, waiting, visits, `revision`), the task (`taskSchema`, `taskBodySchema`, `taskReversalSchema`) and the template. Expressions in `workflow-expr.ts`. Permission: `workflows.manage`.
- Server: `apps/server/src/workflows/`. `run.ts` gathers the trigger's rows, applies `triggerLimits` and opens cases; `engine.ts` (`WorkflowEngine`) advances one case under the `case:<id>` lease, writes it with an expected `revision` (`RevisionConflict` on a stale write), handles waits, time-outs, signals (`emit`) and cancel, and counts down trial; `actions.ts` holds one executor per variant (`EXECUTORS`) and is the one way a step changes a record (prepare + commit as the enabler, within the agent's reach, journalled `via: "workflow"`); `tasks.ts` (`TaskService`) is review, approve (and Always), decline, answer, complete and reverse; `templates.ts`, `draft.ts` (the sentence and at most three questions the chat and builder show), `overview.ts`, `start.ts` (every trigger, and `startFromAgentTool`), `runner.ts` (due workflows, then time-outs, then watched records). Routes: `routes/workflows.ts` (`/api/workflows`, `/api/cases`, `/api/tasks`, `/api/workflow-templates`, and `POST /api/workflow-hooks/:workspace/:token` for webhooks). The hook route needs no principal: its token, minted for one waiting case, is the authority. A Wait step hands it out as `publicOrigin` + `/api/workflow-hooks/<workspace>/<token>`. `WorkspaceHost` routes it by the workspace segment, without resolving anyone, and only to a workspace its `holds` says is there. It is registered `config: { public: true }`, like the booking pages' API (`identity/public.ts`, pinned in `PUBLIC_ROUTES`), so `installIdentity` lets it through without a principal, and the route answers only for its own workspace. A call nothing waits on is not kept. The older `/api/workflow-hooks/:token` still wakes a case on a one-workspace server; it is not open, so through a host it needs sign-in like everything else. Chat: `chat/workflow-actions.ts`.
- **Engine guarantees** (`engine.ts`, tested in `resilience.test.ts`):
  - Nothing is done before it is written down. A step's attempt (operation id `case:node:visit`, its task id) is saved on the case before it starts and marked `executing` just before it acts; the task stores `outcome` and `outputs` before the case moves on. `recover()` (runner) picks up running cases idle for `STALL_MS`: a finished task moves the case on without acting again; an interrupted step repeats only if its variant's `interrupted` is `repeat`, else the task waits as `uncertain` for a person (`/api/tasks/:id/settle` = it happened; approve = run again).
  - A case's last step and its ending are one save (`finish` takes the unsaved case). The ending is saved `announced: false`; `announce` then counts the trial down in one workflow write that records the case in `trialCases` (so announcing again never counts it twice) and emits `case-done` / `group-done` with signal ids of their own making, so `recover()` can announce again without telling twice.
  - Leases are per call (`holder:newId`), renewed each step and by a heartbeat (`heartbeatMs`, default a third of the lease) while a step acts, so recovery elsewhere cannot take a case whose step is still running. A heartbeat that finds the lease gone marks the hold lost; the call then writes nothing more (`Hold.check` after the executor). `engine.create` writes a case without running it; `open` is create then `advance`. A trigger run creates the case, settles the claim, then runs it: a claim is given back only when a lookup answers that the case does not exist; a failed lookup keeps the claim for `reopenClaims`, so an error while the case runs, or an unanswered insert, never opens a second one. `claimFired` is compare-and-set, so two runs never open a case for one record. The claim carries a `pending` open (case id, record, inputs, start, actor); `settleClaim` clears it once the case exists, and `reopenClaims` (runner) opens any claim left pending. A record's count only goes up while the trigger is unchanged (a record that stops matching is marked `lapsed`, not removed), so matching again is a new occurrence with a new case. Child case ids are derived from the attempt, so opening twice opens once.
  - A case follows `definition`, the workflow frozen when it opened (`version` moves on when the graph changes). Approvals carry the task id and apply only to the step the case still waits on.
  - A write review is bound to the task it was opened from (`task.reviews.approve` / `.reverse`: pending id, who opened it, and for an approval the attempt). `approve` and `reverse` refuse any other review with 409 before committing, and the engine checks the binding again before acting. `review()` rebinds when a stale or expired review is refreshed.
  - Every background read goes through `reads.ts` (`mayRead`, `readRecordAs`, `agentNamed`): policy and agent reach at read time, a removed agent parks the workflow. A read that did not reach a record never counts as "not there": a `record_created` baseline grows until one read is complete, `onlyIf` on an unknown record fails (retryable), Look up exposes `complete` and an `incomplete` outcome.
  - `node.retry` retries only `retryable` failures (not sent, 429, model errors), backing off ×2; `uncertain` failures (may have arrived) never retry. A webhook 5xx is retryable only with the step's `idempotent` setting (the receiver honours `Idempotency-Key`); otherwise it is uncertain. A webhook that got no answer is retried only when `env.post` throws `DeliveryError` with `sent: "no"` (`deliveryErrorOf`: the address guard, or a system code such as ECONNREFUSED); anything else is uncertain.
  - Signals are kept (`SignalStore`). `take` claims one for a case, which may take it again until it `ack`s it; the engine acks only after the task it caused is written. No other case can take a held signal. A case entering a wait takes one that came first; `deliverPending()` retries busy or interrupted cases. A decision wait on an already-answered Ask goes straight on.
  - A wait stores the agent its step acts for (`waiting.agent`); polling reads as that agent.
  - A step that enters waiting writes its wait and its outputs on its task first; `waitingOn` puts the case to waiting from that task, in a normal run and in recovery alike. A retry's task records the tries made, and `waitingOn` restores the count from it.
  - Event against deadline is settled under the case lease by the signal's arrival time: a time-out first takes any signal that arrived by the deadline (`take(..., until)`), and a signal that arrived after the deadline times the wait out, whichever is handled first.
  - `cancel` marks the case `cancelRequested` in its own save before cancelling its children, so a child's ending wakes a case that then ends as cancelled; a waiting case is ended under its lease, a running one at its next step.
  - Children: `run_workflow.start` with wait follows how the child ended; `run_workflow.each` fixes `groupSize` before the first child starts, so `group-done:<attempt>` comes only when the whole group exists and has ended, and the join re-checks the cases themselves; call chains are capped at `MAX_CALL_DEPTH` and loops refused when saved (`callLoop`) and at run time; cancelling a case cancels its open children.
  - A pass over many cases (`timeouts`, `deliverPending`, `recover`, `pollRecords`) reports one case's error as a `case.error` event and goes on to the rest.
- Model calls go through `env.llm(task, model?)`; tasks `outreach`, `agent-reply`, `agent-tools`, `think`, `wait-match`, `workflow-draft` each `follows: "chat"` (`models.ts`), and a node's `model` overrides as `task@model`.
- **Workflows never call `composeResponsePrompt`.** Only an `outreach` step's conversation uses an agent's reply prompt, and that arrives with Comms.
- Web: `apps/web/src/agent/workflows/` (`WorkflowsSection`, `WorkflowEditor`, `Canvas`, `StepPanel`, `TaskCard`, `fields.tsx`, `draft.ts`). The agent Tools tab's "Run a workflow" lists workflows whose trigger is `agent`.

## Evals (scenarios, sandbox, checks)

- Spec: `packages/spec/src/eval.ts` (`scenarioSchema` with `turns`, `persona`, `world`, `checks`, `scriptedModel`; `checkSchema` rule | judge; `evalRunSchema` whose `events` are an append-only `RunEvent` log; `verdictSchema` with `said`). Rule checks are `@freebirdai/expr` over the tasks a run left: `where` picks tasks, `expect` all | some | one | none.
- Server: `apps/server/src/evals/`. `Sandbox` (`sandbox.ts`) is a session over `fake()` (`workflows/testing.ts`): start, `step(turn)`, `runUntilWaiting`, `snapshot`, `restore`, `stop`; its own clock and a scripted model, a recording sender and write service, nothing real. Turns are `message` (starts `message_received` workflows), `booking` (starts `booking` workflows with the payload's row), `record` (changes the connection's rows), `clock` (moves time); each is followed by runner passes until nothing changes. Worlds by name in `worlds.ts`. `runScenario` (`runner.ts`) logs turn → step/task → snapshot → verdict after every turn; `checks.ts` scores tasks (the same code will score live tasks). Packs in `evals/packs/`.
- `pnpm eval:scenarios` (`src/eval/scenarios.mts`) runs the packs scripted and exits 1 on a failed rule check; CI runs it, and `evals.test.ts` runs every pack too. Protocol: `bench/PROTOCOL.md`, "Agent-behaviour scenarios".
- **Inputs arrive only as turns.** A workflow step never reads the wall clock, randomness or a global model: `env.now`, `env.newId` and `env.llm` only, or a replay stops matching. **A sandbox cannot reach the world**: never give `Sandbox` a real `OutreachSender`, write service or secrets.
- **Rules gate, judges inform.** Without a judge a judge check is `unsure`.
- In the product (phase 1): a workflow's `checks` are standing rule checks; the engine scores each task as it finishes (`writeTask` → `scoreTask`: `all`/`none` rules whose `where` picks it) into `task.eval`, shown as a badge on the task and the Overview. Approving can change what was proposed first (`approve(..., { edits })`, not for a change to an account); the task records `edited` (each setting before and after). `taskLabel` (spec) reads what people did as labels: good, partly_wrong, wrong, wrong_shipped, delivery. `EvalService` (`evals/service.ts`, `routes/evals.ts`) holds the Test button's sessions (`/api/evals/sessions`: start, step, finish, events as server-sent events), the workflow's pack (`workflow-pack.ts`: turns from its trigger, base checks plus its own), kept runs (`dash_eval_runs`) and the Evals tab's trend. A `start` turn runs a manual or agent workflow.
- Leaving trial on evidence (`workflows/graduation.ts`, `DASH_EVAL_GRADUATION=on`, `env.graduation`): the trial count no longer goes down; an outside step is proposed for Auto when its scenarios pass on this version and enough trial tasks were approved as proposed (`DEFAULT_CLEAN_CASES`), with none declined or reversed. A person accepts it (`POST /api/workflows/:id/steps/:node/graduate`), which sets `node.graduated`, and `nodeMode` lets a graduated step run as its mode in trial. A failed standing check or a reversal puts it back on Approve with `node.demoted`. Graduation is the server's: a save keeps it, and drops it when the step's action or settings change (`ownGraduation` in `workflows/service.ts`).

## Live mode, chat tools, screen review (Dash Evals)

- Live mode (`runLive`, `RunOptions.live`): a real model runs the workflow's steps in the sandbox (`SandboxOptions.llm`) and another plays the persona, writing each email from its goal, manner and the replies it got (`ScenarioSession.personaWrites`); k runs give each check's pass rate. `pnpm eval:scenarios --live [--k 3] [--only id,id]`: needs an AI key, spends tokens, never fails the run, never in CI. A persona with `driver: "model"` runs only live; `person` is still refused.
- Chat (`chat/eval-actions.ts`, on the workflows screen when `BuildChatRegistryInput.evals` is given): `run_scenarios` (the workflow's pack, plus outside personas from the inbound pack aimed at a workflow an email starts: `personaPack` in `evals/workflow-pack.ts`, checked that nothing beyond answering the sender ran unattended), `save_task_as_scenario` (preview first), `explain_eval` (a task's verdicts, what a person changed, or a run's).
- Screen review: while it watches, each email it would have held is marked Good catch or This was fine (`POST /api/inbound/screens/:id/review`; `GET /api/inbound/review`). `GET /api/inbound/readiness` says whether holding is earned by `inboundSettings.holdWhen` (`minScreened` 100, `minDays` 14, `maxFalseFlags` 0.1 by default), and what is missing; a flagged email nobody looked at blocks it. Dash suggests Start holding; a person turns it on.

## Outside agents over MCP (Dash Evals phase 4)

- `routes/outside-mcp.ts`: `/api/public/<workspace>/mcp` (POST, GET, DELETE; in `PUBLIC_ROUTES`), Streamable HTTP with JSON answers, one guide MCP server (`@freebirdai/mcp`, read-write) per session so confirmation tokens stay with it, 60 calls a minute per address, at most 200 sessions idle 30 minutes. Off until `inboundSettings.outsideAgents`; each tool refuses in words while off.
- `outside/registry.ts` is the whole surface, one `business` component: `list_services`, `find_times`, `request_appointment` (held 4h for the person to confirm, as on the public link, contact made unverified) and `send_message` (screened by `InboundService.screen` with mailbox `mcp`; if it passes, `proceedArrival` starts email workflows with the words given, so the case carries the mark). **Never the team's chat registry.** Every call names the email it acts for and goes through `InboundService.gate`. What it returns is only what the public pages show. The agent's own name (its user agent) is recorded on a request; it is said, not proven, and raises no trust.
- Voice is not built: inbound and outbound calls wait on a real `OutreachSender`, and the plan leaves the call engine (a partner's or FreeBird's own) to be decided first.

## Live scoring (Dash Evals phase 3)

- Booking pages: `routes/public.ts` asks the requester policy (`InboundService.gate`, keyed to the booking's email) before Start, Request and Cancel: a blocked sender or domain is refused (403); past `bookingsPerDay`, `openHolds` or `cancellationsPerWeek` it is refused (429) once holding is on, and only counted while the screen watches. A trusted sender is never limited. Refusals and would-be refusals are kept as screen records with `channel: "booking"`. The approval page answers only members holding a link minted for them, so the policy does not apply there.
- Judges (`evals/judge.ts`): `TONE_RUBRIC`, `judgeMessage`, `calibrate` (approved as proposed should pass; edited, judged on what was first proposed, or declined should not) and `modelJudge`, which is `unsure` until the rubric agrees `AGREEMENT_NEEDED` over `EXAMPLES_NEEDED` examples and reports its agreement in every verdict. A workflow with an outreach step gets `toneCheck` in its pack. Judges run on the `think` model task; calibration is `POST /api/evals/judges/tone/calibrate` (one model call per example). Calibrations, saved scenarios and the weekly settings live in `dash_eval_meta`.
- Save as a test (`evals/from-task.ts`, `POST /api/tasks/:id/save-as-scenario`): the case's stimulus and the workflow as the case ran it, people replaced by stand-ins (`evals/redact.ts`: emails, phones, account numbers, link secrets, the case's names), plus a `not-again` check for a declined, edited or reversed step. Saved scenarios join the workflow's pack.
- Weekly summary (`EvalService.weeklySummary`, `sendWeekly`; runner pass "eval summary"): off until turned on (`PUT /api/evals/settings`), to the listed emails or the whole team, through the server's system mail; recorded before sending, so a failed send is not repeated that week.
- Web: `agent/workflows/EvalSettingsPanel.tsx` (weekly summary, Tone judge calibration) under Waiting for you; "Save as a test" on a finished task.

## Inbound screen (Dash Evals phase 2)

- Spec: `packages/spec/src/inbound.ts` (`REQUESTER_TRUST` blocked | unknown | known | verified_agent | trusted, `requesterRuleSchema` keyed `address:` or `domain:`, `inboundSettingsSchema` with `observeOnly` (default on) and per-sender and per-domain daily limits, `screenRecordSchema`). Contact fields gain the weakest source `inbound`: a value a model read from an email. `fieldValueOf(..., { trusted: true })` leaves it out, and scheduling never trusts it.
- Server: `apps/server/src/inbound/`. `screen.ts` (`screenEmail`) is pure rules: a person's rule for the address, then its domain; limits; known injection shapes; someone outside claiming a member's address or to be in charge; risky links and attachments (noted, never held for). `InboundService` screens every new email in Comms' `received` before extraction, highlights and workflows, keeps the result (never the message: it stays sealed in Comms), and holds it only when holding is on, except a blocked sender, held always. Release re-reads the message from Comms' kept 100 and goes on (`proceedArrival` in `server.ts`); Block and Trust set a rule (address or domain). Routes: `routes/inbound.ts` (`/api/inbound/…`, `workflows.manage`). Tables `dash_inbound_screens`, `dash_inbound_rules`, `dash_inbound_settings`.
- **Values an email chose never drive an outside step on Auto** (`workflows/inbound-mark.ts`): in a case an email started (`start.kind === "message"`, row `inbound.trust` not `trusted`), an outside step whose non-word settings read anything but the sender, the mailbox or the contact's own keys and record- or member-given fields runs on Approve, saying which settings came from the email. Paths come from `@freebirdai/expr`'s AST; one that does not parse counts as marked. Words a step writes (subject, wording, instructions) may quote the email.
- Sandbox: a `message` turn is screened by the same `InboundService` (world `workspace.inbound`: settings, rules, members); a held email starts nothing and is listed in the run's `ended` intents. The inbound pack (`evals/packs/inbound.ts`) has the six personas, dev only: held-out ones must be written apart.
- Web: `agent/workflows/HeldEmails.tsx` (held emails with Release, Trust sender, Block sender, in Waiting for you and Comms; the screen's settings and rules under Waiting for you).

## Calendar, scheduling, contacts and bookings

- Calendar spec: `packages/spec/src/calendar.ts` (`calendarEventSchema`: `kind` event | deadline | appointment, `status`, `source`, `dedupeKey`, `pinned`; old `deadline: true` rows read as `kind: "deadline"`). Server: `apps/server/src/calendar/` (`CalendarStore` with `upsertByKey`, `CalendarService`), `routes/calendar.ts`; the chat reaches it through the screens below. A workflow's entries are keyed `workflow:rowKey:node` and follow their records each run (`workflows/calendar-sync.ts`); an entry a person changed is `pinned` and left alone. Appointments change only through their booking. Permission `calendar.manage` (owner, admin, editor).
- Scheduling spec: `packages/spec/src/scheduling.ts` (profiles, pools, appointment types, blocks set | blank | closed, placements with `recurrence`, settings layered workspace → host → type → block by `resolveSettings`). Server: `apps/server/src/scheduling/` — pure `zoned.ts` (wall time via `Intl`), `recurrence.ts`, `rules.ts` (three-valued: eligible | ineligible | unknown, with `trusted`), `slots.ts` (`findSlots`, the only code that decides availability), `assign.ts`, `discover.ts`; `SchedulingStore` (`dash_scheduling`), `SchedulingService`, `routes/scheduling.ts`. Blocks are match-only, never a preference. An appointment type's `eligibility` ("Who can book": rules over contact fields and the type's own `request.*` questions, `whenUnknown`, and a `message`) is checked first in `findSlots` (`typeEligibility`): not taken means no slots and `notEligible`, said in the type's words on the booking page, by agents, and as a 403 from `BookingService.request`; the team's bookings follow it too. Someone turned away (on the booking page, the public link, by an agent, or a request) is a `turned_away` outbox event (`BookingService.turnedAway`), id'd once a day per person and type in their zone; it has no booking, so `BookingDispatcher` only starts workflows on it, with `WorkflowBookings.turnedAwayRow` as the row (`contact.*`, `type.*`, `request.*`, `answersText`, `reason`, `via`, `viaWords`). The built-in "Follow up with people turned away" template (`recipe-turned-away`) texts them, or emails them with no phone, then notifies the team; the type editor makes one scoped to the type (`types` on `POST /api/workflow-templates/:id/workflow`).
- Contacts spec: `packages/spec/src/contact.ts` (`contactSchema`; fields keep each value by where it came from — `record` with its `ref`, `person`, `member` — and `fieldValueOf` picks member > record > person; `normalizeEmail`, `normalizePhone` → E.164). Server: `apps/server/src/contacts/` — `ContactDirectory` (`directory.ts`) is all scheduling may use and what a CRM must keep; `ContactService` is the only code that reads or writes a contact; `ContactStore` claims each email or phone in `dash_contact_keys` in the same transaction as the save. Matching reads as the rule's `savedBy` through the workflows' reader and policy; exactly one record links, several leave a pick on the contact, and a refused, failed or unfinished read is `unavailable`, never "none". Values copy once; Refresh and Unlink are explicit. Permission `contacts.manage` (owner, admin, editor); reading contacts needs `records.read`.
- Bookings spec: `packages/spec/src/booking.ts` (`bookingSchema`: pending | confirmed | suggested | denied | cancelled | expired | completed | no_show; `holdsOf`, `dueAt`) and `booking-events.ts` (`BOOKING_EVENTS`, kept apart so `workflow.ts` can read it without importing scheduling). Server: `apps/server/src/bookings/` — `BookingService` is the only code that changes a booking. Each change takes the locks of every host it touches (`BookingStore.withHosts`: advisory locks in Postgres, a per-host queue in memory, in name order), re-checks the time with the slot engine, and writes the booking and its event (`dash_booking_events`) in one transaction. **Inside `withHosts` read nothing but the transaction**: PGlite has one connection, so any other read waits for ever. Read a `SlotContext` (`SchedulingService.context`) before the lock and search it with `slotsIn` inside. Routes: `routes/bookings.ts`.
- Bookings in workflows: the `booking` trigger; `workflows/booking-events.ts` (`BookingDispatcher`) delivers the outbox as a runner pass and right after each change: calendar mirror, the `endWhenCancelled` stop, every case waiting on `booking:<id>` woken with the event directly (several workflows may wait on one booking, so no single-use signal), new cases with ids from workflow + event, then contact counts. Steps in `workflows/schedule-actions.ts` (`ask.booking`, `wait.booking`, `wait.appointment`, `schedule.*`, `outreach.inform`); each reads the booking rather than trusting the event, so a repeat is harmless. Recipes ship as built-in templates (`workflows/recipes.ts`).
- Public pages (no sign-in): `/p/<workspace>/book/<token>` (a contact's own page), `/p/<workspace>/t/<slug>` (a type's public link) and `/p/<workspace>/approve/<token>` (a member's approval page), over `/api/public/<workspace>/…` in `routes/public.ts`. **Only routes registered `config: { public: true }` skip identity, and `PUBLIC_ROUTES` pins the set** (a test compares it with `publicRoutesOf(app)`); add a public route there or it wants sign-in like any other. GET never acts; every change is a POST with the token. Tokens are kept only as hashes (`public/tokens.ts`), so a link is minted whenever one is handed out (`bookings/links.ts`: `BookingLinks.contactLink`, `bookingLink`, `approvalLink`). A link made on the public link (`fromPublic`) shows and changes only bookings made through it, and a public form never adds to an existing contact (`findOrCreate({ unverified: true })`): anyone can type an email. Approve a booking asks each member who may answer once per try of its step (`askTeam`), reminds once after `remindAfter`, and revokes every link when it ends (`closeAsks`); the approval page re-checks membership, the step's task and attempt, and the booking on every answer, and spends the token after the booking changes. `WorkspaceHost` routes a public path by the workspace it names, with no principal, and only to a workspace its `holds` says is there.
- Booking in conversation (plan B11): a `schedule_appointment` agent tool (`schedule: { types, offer }` on `agentToolSchema`; empty types means every active one) gives the agent's reply loop eight tools (`scheduling/conversation.ts`: `find_times`, `check_time`, `request_appointment`, `appointment_status`, `respond_to_suggestion`, `cancel_appointment`, `reschedule_appointment`, `send_scheduling_link`), and `composeResponsePrompt` adds a "Booking appointments" section only while such a tool is on. Tools speak wall times in the person's zone (`at`: "2026-10-13T09:00", plus `when` words), so the model never converts a time. **A reply may not name a clock time that no tool returned this turn** (or that was already in the conversation): `replyWithScheduling` asks once for a rewrite, then answers without a time and sets `needsReview`. Tool results go back as a user message marked as data, since adapters drop `tool` messages. The tool's mode applies: `approve` asks approval for every request, `deny` answers with `denyReply` and never calls the model. Until Comms, `POST /api/agents/:id/tools/:toolId/use` with `{ inputs: { contact, message, history?, channel? } }` runs one reply on the `agent-reply` model.

## Communications (email)

- A mailbox is a connection with `mailbox: { provider, address, owner }` (`connect-spec` `connection.ts`), made from the shipped `dash/catalog/gmail.json` or `outlook.json`. The owner (`{ kind: "team" }` or `{ kind: "agent", id }`) decides the area: Your comms, or that agent's area under Agent comms. Mail never moves between areas; changing the owner only moves where a mailbox is shown. The OAuth app is the server's own when it has one (`DASH_GOOGLE_CLIENT_ID|SECRET`, `DASH_MICROSOFT_CLIENT_ID|SECRET` → `BuildServerOptions.mailApps`), so people only sign in; otherwise a workspace pastes its own once per provider (vault `comms-app-<provider>-id|secret`, which wins over the server's). Either is copied into each mailbox's own refs; sign-in is the engine's OAuth (`POST /api/connections/:id/oauth/start`).
- Spec: `packages/spec/src/comms.ts` (`MailMessage`, `MailDraft`, `CommsState`, areas, `parseMailQuery` / `matchesMailQuery`, `ignoredAddress`). Server: `apps/server/src/comms/` — `gmail.ts` and `graph.ts` are the `MailProvider`s (they read only through the engine's read, bound to the mailbox, and say what to send as a write intent); `search.ts` turns the query into Gmail `q` or Graph `$search`; `CommsService` (`service.ts`) is the only code that reads mail, keeps the newest 100, sends, and decides who may send; `CommsStore` (`store.ts`; tables `dash_mail_recent`, `dash_comms_mailboxes`, `dash_comms_state`, `dash_comms_drafts`, `dash_comms_settings`). Routes: `routes/comms.ts` (`/api/comms…`).
- **Kept: the newest 100 per mailbox**, headers and snippet only, sealed with the vault's key (`DbCommsStore` takes the vault as its `RowCipher`): the second "no disk cache" exception. Past them a list reads the provider's own pages live. The merged list's cursor holds a position per mailbox (`{k}` in the kept, `{t,i}` in the provider's pages skipping the kept, `{s,i}` in a search).
- **Sending is always the write service's review.** Gmail's `send` is a declared action on `message` (`POST /messages/send`, the body MIME at `raw`); Outlook's is `POST /me/sendMail` with the MIME as the body. "Save as draft" is the provider's create-draft. A draft an agent wrote goes from its own mailbox, or from a team mailbox only when its reach has `records.act` on that connection (the agent page's "Email it sends from"); another agent's never (`CommsService.agentMaySend`).
- New senders become contacts (`origin: "email"`), never the workspace's own addresses or the ignore list (`commsSettings.contactIgnore`), and a new contact is matched once. Mail that arrives after a mailbox's first read starts `message_received` workflows (case id from workflow + mailbox + message). A runner pass reads each signed-in mailbox every 5 minutes.
- Workflows: **Reply to the email** (`outreach.reply`, `workflows/actions.ts`): the agent writes a reply on the `outreach` model task with its reply prompt. `send: approval` (default) leaves the draft in Comms and waits on `draft:<id>` (outcomes `sent`, `saved`, `discarded`, `timed_out`); `automatic` reviews and commits it as the workflow's actor. Keep the node's own mode `auto`: the step's `send` setting is its approval.
- Web: `apps/web/src/comms/` (`CommsShell` three panes, `model.ts` areas and remembered ticks, `ThreadView` with drafts and the review, `MailboxSheet` add and manage); styles `packages/react/src/styles-comms.ts`. Tests: `comms/comms.test.ts` against `comms/fixtures.ts`, a fake Gmail and Graph answering the shipped entries.
- Agents starting conversations: Outreach email (`outreach.email`, `outreach.inform`) goes through `CommsService.sendNew`, from the agent's own mailbox or a team one it may send from, as the workflow's actor, at most once per step key (`out-<hash>` drafts). A reply (same thread, or the same subject from the address it went to) emits `reply:<draft>` for a Wait for a reply. A host's own `outreach` option still wins; texts and calls stay not sent.
- Team notices: `comms/notify.ts`. `TeamNotifier` (bookings) and `HighlightNotifier` send through the system mail reports use (`DASH_EMAIL`, `BuildServerOptions.email`), to each member's email or `CommsSettings.noticesTo`, each at most once (`dash_comms_notices`). Highlights are checked on new mail in an agent's own mailbox (model task `agent-tools`).
- Contact fields from email: `ContactFieldDef.fromEmail` (`look` in plain words); `comms/extract.ts` reads each new email once on the `extract` task for the fields still empty from anyone, before workflows see the contact; values are the person's own (`record(..., "person")`).
- Contact types: `ContactMatchRule.type`; `contactTypes` (spec) is the types of the rules a contact is linked by, given as `contact.types` in booking, turned-away and email rows. The step editor's "Contact type is…" writes `contains(contact.types, "X")` or `len(contact.types) == 0`.
- Calendar sync: `mailbox.calendar` (`member`, `busy`, `push`; `PUT /api/comms/mailboxes/:id/calendar`, which records who turned push on as `MailboxMark.calendarBy`). Gmail lives at `www.googleapis.com` (`/gmail/v1/users/me/…`) so its calendar (`/calendar/v3/…`) shares the host; scopes add `calendar.events` / `Calendars.ReadWrite`, so existing mailboxes sign in again. Busy: `SchedulingDeps.external` → `CommsService.busy` (live through the engine, free, cancelled and all-day events and Dash's own pushed events left out; an unreadable calendar adds nothing and says so on the mailbox). Push: the "calendars" runner pass (`pushCalendars`, also `POST /api/comms/calendar/sync`) writes each member's appointments (now − 1 day to + 90 days) through the write service as that person, keyed in `dash_comms_calendar` with a digest so only changes are written; cancelled or removed ones are deleted.
- Keeping up: `MailProvider.changes(cursor)` — Gmail `history` from the history id, Graph's inbox `delta` (`$deltatoken=latest` to start) — kept as `MailboxMark.historyId`; the newest page is read instead the first time, when the record is gone, and every 30 minutes (`fullAt`).
- Contacts from Comms: `ContactService.merge` (the other's id becomes an alias key, `alias:<id>`, so `get` still finds it; `BookingService.moveContact` re-files bookings); `byEmail`; `matchAll` (`POST /api/contacts/match-all`); a new contact is matched once and announced (`settle`, `ContactDeps.created`) — by Comms for an email sender, in the background only while a `contact_created` workflow listens (`wantsCreated`), so matching otherwise stays explicit. `GET /api/comms/contacts/:id/messages` (kept mail plus each provider's search); a thread answers with its sender's contact card. `POST /api/comms/backfill-fields` reads the kept 100 for fields set to fill from email. The chat's `set_contact_field` takes `fromEmail`, `set_match_rule` a `type`.
- Agents: a `search_mail` tool (`CommsService.searchAs`: its own mailboxes and team ones its reach reads) offered to Reply to the email, up to three searches, results handed back as data. Marks: `POST /api/comms/messages/:mailbox/:id/status` (`triaged` "Handled", `ignored` "Set aside", `new`). A person's sent email is on the chat timeline (`comms/timeline.ts`, kind `email`).
- Texts and calls: see Dash Phone below.

### Building a line source

What a host implements, and nothing else changes outside it:

1. **`PhoneLineSource`**, passed as `phoneLineSource`:
   - `offers(workspace)` → `PhoneLineOffer[]` (`id`, `title`, `description`, `areaCode`): the cards Add a phone line shows first. Return none to show nothing.
   - `provision({ workspace, offer, areaCode? })` → `ProvidedLine` (`provider`, `number`, `ref`): make the number on the host's account. `provider` must be an id in `phoneProviders` (register the host's adapter there if it is not one of the defaults). `ref` is the host's own id; Dash keeps it on the line and hands it back. Dash then routes the number's texts to the line's webhook with the keys below.
   - `keys({ workspace, line, ref })` → the provider adapter's keys for one use (for Twilio, subaccount keys). Synchronous, so cache what you fetch; Dash calls it for every send, webhook check and registration call, and stores nothing.
   - `registration?({ workspace, line, ref }, keys)` → a `RegistrationAdapter` for the line, when the host registers its lines its own way; `undefined` uses the provider's. The wizard and its checks are the same either way.
   - `suspended?({ workspace, line, ref })` → `{ reason? }` or null, read before every send and call; the line shows "Suspended by the provider of this number".
   - `release({ workspace, line, ref })`: give the number back. Called when the line is removed (and with `line: ""` when wiring a just-provisioned number failed). Dash has no workspace removal yet; when it does, it removes each line, which releases it.
2. **`PhoneUsage`**, passed as `phoneUsageEvents`: `record(event)`, keeping the first event per `key`. Kinds: `text_sent`, `text_received`, `call_minutes`, `number_held`, `number_released`, `registration_submitted`; `provided` says whether the line came from the line source.
3. Optionally a provider adapter in `phoneProviders` if the host's lines run on one Dash does not register by default.

Nothing outside the host's own code names the host: the seams, the setup card and the suspended chip all read the host's words.

## The chat on every page

The chat is its own way through the app: anything on a page can be done by hand, and anything can be asked for in the chat, which says what it will do on a card and does it on Approve. Nothing the chat does lives in a Dash binding: each page is a guide component with its actions, what is on screen reaches the model through guide (`activeComponentIds`, `focus`), a change leaves a chip, and "take me to …" or "show me …" moves the page through guide's navigation. Dash registers the pages and reads the data; guide does the rest.

- Screens: `packages/spec/src/screens.ts` (`DASH_SCREENS`: id and page for `calendar`, `bookings`, `types`, `blocks`, `people`, `settings`, `contacts`, `contactFields`), shared by server and web so ids cannot drift. Server: `apps/server/src/chat/screens/` (one file per screen, `buildScreens` in `index.ts`), registered after the board's widgets in `chat/registry.ts`; `chat/handles.ts` keeps a widget from taking a screen's id. The screens, agents and workflows (`appWide` in `server.ts`'s registry callback) are registered whether or not a dashboard exists, so a workspace that uses only the calendar still has the whole chat (`no-dashboard.test.ts`). Shared helpers in `common.ts`: `allowedTo` (each action's `authorize`, the boundary for chat and MCP alike), `blocked` (a preflight problem the chat can fix), `findBy` (by id or name), `changeRows` (before → after rows for the card) and `landed` (`withCitation`: the chip under the outcome that opens the screen and rings the item).
- Every change is `requiresConfirmation: "preview"` with a preview built from the setup snapshot the registry was built with. The registry is cached for 60s and rebuilt after any setup change (`SETUP_CHANGES` in `server.ts`, and `changed()` in each handler), so a card's "before" is current. Preflight resolves names to ids and fills `current` for bookings, contacts and entries.
- A link that is itself a key (a booking page, an approval page, a calendar feed, a contact's page) is returned with `withTransient`: the person who approved sees it once on a card in the chat (`OnceCard`), and guide's server keeps it out of the conversation and every event. Never put such a link in a summary.
- Server options: `harnessArgsMode: "catalog"` (one `start_action` for the whole app; the picked action's own schema on `update_action_args`), `navigation: { enabled: true }` (`open_component` for "take me to …"), `maxToolSteps: 5`. No tool budget.
- Prompt caching works with or without the provider. Each turn's first step opens with the tools, `CHAT_SYSTEM_PROMPT` and the list of actions, byte for byte the same whatever is asked or on screen (`no-dashboard.test.ts`), so OpenAI and open-source servers that cache a repeated prefix reuse it unasked; the guide engine marks the end with `cachePoint`, and `anthropicSystem` in `llm.ts` turns that into Anthropic's cache point. Keep anything that changes per turn out of `CHAT_SYSTEM_PROMPT` and the tool descriptions, or every turn pays for the whole prefix again.
- Web: `apps/web/src/agent/chatScreen.ts`. `useChatScreen` makes the screens on show active (context, never a limit), `useChatFocus` names the item open, `screenAttrs` / `itemAttrs` put `data-freebird-component` / `data-freebird-item` on the page for citations, and `useScreenChanged` reads a screen again after `announceScreenChange` (sent by `ChatColumn` when an action on that screen runs). `ChatActionCard.tsx` is the approval card (`.dash-action-card*`) and the shown-once card (`.dash-once*`), styled in `packages/react/src/styles-chat-cards.ts`. A chip or a navigate request goes through `goToCitation` (`MessageExtras.tsx`): `activateCitation`, then `showElement` rings the setting. Nothing moves the page unless the person clicks or asks.
- Adding a setting: add it to the screen's action schema and preview (with `changeRows`), give the element on the page `itemAttrs`, and add a case to `screens.test.ts`.
- Workflows and agents (`DASH_SCREENS.workflows`, `.agents`) are their own components, registered by `buildChatRegistry` from its `workflows` / `agents` ops (no longer on the `dashboard` roster). Each change leaves a chip to the item's own page (`#/agent/workflows/<id>`); `WorkflowsSection` and `AgentsSection` report themselves and the open item and reload on `announceScreenChange`.
- Dashboards: the open tab is the `board` component (registered only for a real board; its page is `#/d/<id>`). `ChatScopeReporter` reports it, and the open record as its focus, only while a board, widget record or record page shows (it is mounted everywhere, and `useChatScreen([])` reports nothing rather than clearing another page's report). The `x-dash-*` headers stay as the inputs Dash reads the board's data with; `describeScreen` now only says whether the open record's fields are in hand.
- "Show me" actions need no approval and return `withNavigation`: `open_widget` (optionally with a `preset`), `switch_dashboard`, `set_time_range`, `open_connections`. Guide's client goes there like a chip; board addresses carry `?range=<preset>` and `?panel=connections` (`route.ts`), which `BoardAsk.tsx` applies through the range control and the panel, then drops from the address. Approved board changes (`create_dashboard`, `rename_dashboard`, `remove_widget`, grouping, `read_connection`) leave a chip and move nothing. `ChatColumn` no longer acts on any of them; it only re-reads what changed.
- A question about another period is answered without moving the board: `answer_from_data` takes `from` / `to` (days in the reader's calendar), and the read uses them in place of the tab's range (`context/period.ts`). The engine's `turnNote` gives the model today's date and the tab's window each turn, after the cache point.

## Chat topics and the timeline

- A topic is a chat session: `freebird_chat_session.id` is the topic id, `title` its name, so a message's topic is its `session_id`. No guide schema change.
- Server: `apps/server/src/chat/topics.ts` (`TopicStore` reads one person's topics by day across sessions; `decideTopic`; `withTopicContext`). Routes in `routes/chat-topics.ts`: `POST /api/chat/route` (which topic the next message goes in, called before every send), `GET /api/chat/days`, `GET /api/chat/day/:date` (topics plus finished workflow runs and done tasks), `GET /api/chat/messages?day=`. All take `tz` so days are the reader's own.
- The model's context on a chat turn is the current topic plus the earlier topics that are both among the last 2 and active in the last 24 hours (the smaller window wins). `withTopicContext` adds them as one system note, only when `auth.extra.turn` is set (`POST /freebird/chat`); the history route sees the store unchanged.
- Topic rules: "new topic[: name]" always splits; a person's first message of a day starts a new topic; otherwise the `context` model task picks among the current topic, the 2 before it and the one jumped to from the timeline. No model, or a failed call, stays put.
- Web: no "new chat" button. `ChatColumn` loads today from `/api/chat/messages`, lazy loads neighbouring days past the top (and, after a jump, the bottom) border, merges the store's live messages (`chat/stream.ts`), and shows "↓ Latest". `chat/Timeline.tsx` is the Timeline tab: the last 7 calendar days as tiles (empty ones muted, no counts), "Later" for a month calendar (`chat/calendar.ts`, activity read with `chatDays` 120 at a time), and the picked day's topics and tasks below, each topic opening the chat at its first message. In the stream a topic divider shows only for a named topic whose name differs from the one before; unnamed topics ("Earlier chat") never get one, and `data-topic-start` sits on each topic's first message per day. Its CSS is `.dash-chat-timeline__*` (the Timeline widget owns `.dash-timeline__*`).

## Conventions

Mirrors the FreeBird monorepo: `"type": "module"`, tsup ESM builds, zod ^3 as a peer, vitest, per-package `tsc --noEmit`, `workspace:*` internal deps. Packages should be foldable into the OSS FreeBird monorepo later without rework.

The `LlmAdapter` / `LlmTool` / `LlmStreamChunk` interfaces in `@freebirdai/dash-agent` are copied byte-for-byte from `@freebirdai/core`'s `adapters/llm.ts` so `@freebirdai/adapters-llm-openai` and `-anthropic` drop in unchanged once published. **Do not drift them.**

## Hard rules

- **No in-process `eval`, no `new Function`, no third-party JSONPath library.** Grafana's JSON API plugin shipped an XSS because `jsonpath-plus` allows embedded subexpressions implemented as arbitrary JavaScript. `@freebirdai/expr` is hand-rolled and parses to an AST. The one place code that is not this repository's runs is connector code, and only inside the `ConnectorSandbox` (below) — never in the server's process, the browser, or `@dash/expr`.
- **Connector code is contained by its authority, not trusted.** For what a connection cannot describe in data — signed requests, a login for a session token, a read in several steps — a connection carries `connector` code (`packages/spec/src/connector.ts`), written by the `connector` model task at configuration time and pinned by its SHA-256. It runs in `QuickJsSandbox` (`connect/packages/connect/src/connector/`): no network, file system or clock of its own, capped memory, CPU and wall time. Every request it makes is decided by `host.ts` against the connector's authority: listed hosts and methods only (GET, HEAD, POST — never a change), a credential filled in (`{{secret:name}}`) only for a host bound to it, signatures made server-side, downloads only at an address the API gave, echoed credentials removed. Where the connector declares request templates (`authority.templates`: method, host, path, purpose, credentials, body keys), a request no template allows is refused before it leaves. A POST is templated only at a path the documentation names. No template, and no request on any grant, may be one of the catalog's writes, except a sign-in, search or export declared as exactly that. `signRequest` may sign a declared endpoint's request but never move it. Each endpoint may have its own module (`connector.operations`) loaded beside the shared sign-in, so code for one endpoint never replaces another's. Shared code is replaced only when every endpoint it read still reads (`version`, `previous`). **The code never receives a credential value.** A scheme that truly needs raw secret material in code becomes a reviewed built-in signer in the repo (AWS Signature V4: `packages/adapters/src/sigv4.ts`, the `sigv4` sign-in), never sandbox code. The loop keeps code only when a read through it returns records. Controls and residual risks: `PLATFORM.md`.
- **The LLM never runs at render time.** It proposes a spec (or connector code); deterministic code executes it.
- **Pagination is declared or probe-confirmed, never inferred.** A wrong guess doesn't error — it silently returns the first page and a chart that's quietly incomplete. Importers (OpenAPI and prose alike) write guesses to `paginationProposal` only; the integration loop installs a rule (with `paginationChecked`) only when its second page returned new records.
- **Evidence is a ladder, never a flag.** `accepted → advanced → traversed → count-reconciled → metric-reconciled` (`packages/spec/src/evidence.ts`), each with scope, configuration, time and limits. Never write "complete" or "verified" for something only one rung supports.
- **A read's end is observed, never assumed.** Every adapter sets `FetchMeta.completion` (`traversed | partial | unknown`, and why). Only `traversed` supports "read to the end". Connector code that does not say `done: "all"` is `unknown`, whatever it returned. `pages` counts pages of records, never sign-ins (`requests`). A count reconciles only under the read's own scope (`countReconciled`, `scope`/`totalScope`).
- **A read past a tile's limits is carried on, never cached on disk.** A read that stops at its page ceiling or a connector's runs hands back a `FetchMeta.continuation` (never holding a key), and `LongReads` (`apps/server/src/jobs/`) carries it on in the background. Its records and its place are kept in the job store, sealed with the vault's key, only while it runs, and the whole answer goes to the memory cache. That is the one exception to "no disk cache". A key read this way is refreshed through its job, never by a capped read over the whole answer.
- **An endpoint is settled by evidence, never by being started.** `CheckQueue` (`jobs/check-queue.ts`) holds which endpoints are due a check, keyed by the connection narrowed to that endpoint. A check that fails or never reaches an endpoint leaves it due, after a wait.
- **A page drawn by scripts is drawn by Playwright's own Chromium, and every request it makes goes through `fetchPublicDocument`.** The browser's own network is never used, and only reads go. The open-source build downloads Chromium only after the person agrees, once (`RendererTooling`). The benchmark and the tests never download it.
- **A workspace sees only its own.** Each workspace is its own `buildServer` (`platform/workspaces.ts`), with its own folders, its own key in every database store, and its own chat tenant. A new store takes the workspace, as `PLATFORM.md` says. A server refuses a member of another workspace, and every read asks the policy for `records.read`.
- **A repair never moves a key to another organisation.** Address repairs are limited to the documentation's or the current address's domain (`sameSite`), and values come from the API's or the documentation's own words — never guessed. Repairs are a plug-in point: `RepairStrategy` in `connect/packages/connect/src/integrate/strategies.ts`.
- **An incomplete read says so, in plain words, on the tile.** Adapters phrase it with `INCOMPLETE` (`packages/adapters/src/incomplete.ts`) — what was left out, never how much or which way — and `isIncompleteNote` is how every consumer tells those notes from other caveats.
- **Capabilities live in one manifest.** `packages/spec/src/capabilities.ts` says what is supported; importers cite it with `capabilityNote` when an API needs something outside it, and `COMPATIBILITY.md` is generated from it (`UPDATE_COMPATIBILITY=1` on `capabilities.test.ts`). A test fails if the two drift.
- **The benchmark measures; its tests do not pin results.** `apps/server/src/bench/` — providers carry answer keys computed from their own seed, a hand-written `reference` connection proves each key, and the held-out split is never tuned against. See `bench/PROTOCOL.md`.
- **API responses are untrusted input to the LLM.** Truncate, redact, and carry an explicit untrusted-data clause in the system prompt.
- **`runPipeline` takes an injected clock.** No `Date.now()` in the runtime — determinism and testability.

## Writes (changes to connected accounts)

- **`ops` are reads.** Almost always GET; a POST only for an API that reads with a body — a search, a report, a GraphQL query — and then only with a `readSafety` saying why (`opDefSchema` refuses one without, and refuses a GraphQL document that could change anything). A read whose safety rests on documentation or a model rather than the protocol (`safeByProtocol` false) is never warmed by the keeper, never retried, and journalled every time it is sent. Endpoints that change things live in `CatalogEntry.writes` — never in `ops` — so no widget, keeper target, `/api/query`, brief or resource derivation can name one. Only `WriteService` (`connect/packages/connect/src/writes/service.ts`) sends a write.
- **Every secret goes through the credential broker** (`connect/packages/connect/src/auth/broker.ts`, `secretFor` in `server.ts`). For a static key it is the vault's value; for OAuth it is a live token, fetched, renewed a minute before expiry, and renewed again after a refusal — the refused page is read again and the read carries on (`FetchContext.renew`). Never read `keys.get` for a request; never retry a write.
- **Every write is reviewed, then committed.** `prepare` reads the record fresh (never from the cache), builds the exact request and a before/after review, and returns a digest; `commit` sends only a review whose digest matches, once, for the person who prepared it, after re-reading the record and refusing if it moved (409 with a fresh review).
- **A replace (`PUT`) is built from the record, never from the changes alone.** Each request field's `readFrom` says where its current value is shown; fields that cannot be read are listed on the review as "not sent". Settle them with "Match fields" (the `writes` model task) or a person's mapping — never by string similarity at run time.
- **No retries and no redirect-following on writes.** A timeout after sending is reported as "unknown outcome", never as "nothing changed".
- **Chat never prepares at confirm.** The guide harness re-runs `preflight` at the moment somebody clicks Apply and merges its `resolvedArgs`; `change_record`/`remove_record` therefore reuse the review while proposing and only *check* it at confirm (`ctx.auth.extra.via === "confirm"`).
- **Every attempt is journalled and policy-checked.** `WriteJournal` gets a full event (before, sent, after, changed, reversal hint) for successes, failures, refusals and unknown outcomes; `Policy.can` is asked on prepare and again on commit. OSS defaults: `localOwner()`, `ownerPolicy`, `nullJournal` — see `apps/server/src/identity/README.md`.
- **Writes are native to every connection — there is nothing to switch on.** The review is the safety step, and `Policy.can` is the only gate (always yes in OSS). An endpoint read from prose (`confidence: "inferred"`) is offered too and says so on its review; `confirmed: false` (set by `PUT …/writes/:opId/offered`) is the one way to stop offering an endpoint.
- **The browser never holds a catalog entry's `writes`** (`catalogForBrowser`); a save from the browser keeps the server's. An entry whose writes were never read (`writesVersion` absent, `origin: "openapi"`) has them read from its published specification — a docs read, never the account — when a connection is added from it and once per run at startup (`WriteEndpointReader`, `autoReadWrites`, on only in `index.ts`). `IMPORT_VERSION` is deliberately not bumped for writes.
- **Every row that is a record can be changed where it is shown.** Components draw `RowActions` from the optional `rowActions` render prop; the host builds them with `recordChangeRequests` + `changeRowActions` from `recordTargetFor` and the server's `allowed` view, so a row's menu and its click always agree on the record.

## Gotchas (paid for elsewhere, don't rediscover)

- **Vitest runs serial** (`--fileParallelism=false`). Parallel workers flake on the OneDrive filesystem.
- **`zod-to-json-schema` chokes on refinements, records, and unions.** So Dash's adapters use their own `toJsonSchema` (`apps/server/src/llm.ts`), which maps each shape it knows on purpose (scalars, enums, objects, arrays, and for the chat's screens nullable, record, union, refinements as their plain shape, and open objects) and throws on anything else. Zod still validates the arguments when they come back. A new tool shape goes into `toJsonSchema` with a test; `screens.test.ts` sends every screen action through it.
- **The Anthropic adapter defaults `maxOutputTokens` to 1024.** Set it explicitly.
- **Vite proxy keys are plain prefixes.** Use a regex key (`"^/api/"`) or it swallows app routes.
- **Escapes in a Python-heredoc edit script are read twice.** Writing `.join("\n\n")` from inside a `python - <<'EOF'` block lands a literal newline in the file, not the two characters. `HEAD` carried a broken `server.ts` for exactly this reason — a mangled `join` that made the whole file unparseable, so `apps/server` did not typecheck. Build such strings with `chr(92)` rather than trusting the escape, and check the exit code: a loop ending in `; echo ok` reports success it did not verify. A `\b` in a regex fares worse: it lands as a backspace byte (0x08) that no editor shows, so grep a file for `\x08` after such an edit.
- **The sandbox's worker and prelude are plain JavaScript** (`connector/worker.mjs`, `connector/prelude.js`), so a worker thread loads them under tsx, vitest and a build alike with no loader. The prelude runs *inside* QuickJS: it has no Node, no TypeScript and no imports. Opening a run costs ~300 ms (a fresh interpreter each time, deliberately), so a read through a connector is slower than REST.
- **`pnpm bench` never overwrites a result.** A second run the same day gets `-2`, and a `--only` run says so in its name. One once replaced the only copy of a checkpoint's dev run.
- **Never test against a real account without its owner's go-ahead, and never write to one beyond what they allowed.** Prefer the mock providers and public APIs such as JSONPlaceholder. For a browser check, use an isolated `DASH_ROOT`.
- **React controlled inputs ignore direct `.value` writes.** When driving them programmatically in browser verification, use the native value setter plus an `input` event.
